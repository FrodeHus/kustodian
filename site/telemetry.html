Telemetry

Graph compatibility findings

Kustodian can share one kind of data, and only if you say yes: which Microsoft Graph tables refuse which query options. Nothing else is collected, and it is off until you opt in.

Why it helps

Graph doesn’t support every query option on every collection. Some refuse $top=999, some refuse $count, $orderby or $select, some refuse a filter on a nested or multi-valued column, and some won’t list certain columns at all. Kustodian finds out by probing: it sends the request, reads the refusal and tries again without the option. It remembers what it learnt for 7 days, on your machine.

Probing costs time and requests, and some collections, such as sign-in logs, throttle hard. When findings are shared, the ones that hold across tenants can be built into Kustodian, so every user’s queries on those tables skip the probing from the first run.

What is sent

One event each time probing finds something new about a table. The event is exactly this:

{
  "name": "Microsoft.ApplicationInsights.Event",
  "time": "2026-11-02T12:00:00.0000000+00:00",
  "iKey": "<Kustodian's Application Insights key>",
  "tags": { "ai.application.ver": "0.93.0", "ai.location.ip": "0.0.0.0" },
  "data": {
    "baseType": "EventData",
    "baseData": {
      "ver": 2,
      "name": "GraphProbeFinding",
      "properties": {
        "path": "auditLogs/signIns",
        "finding": "refusesTop",
        "detail": "$top"
      }
    }
  }
}
FieldWhat it holds
pathThe table’s Graph path from Kustodian’s built-in schema, such as users or auditLogs/signIns. Never an object ID.
findingrefusesTop (Graph refused the page size), refused (Graph refused a clause) or notListed (Graph won’t serve columns in a list).
detailThe clause ($count, $orderby, $select, or the filtered column, such as proxyAddresses/any), or the column names from the schema.
ai.application.verKustodian’s version, so a finding can be matched to the code that made it.
ai.location.ipAlways 0.0.0.0, so Application Insights derives no location from your address.

Never sent

  • Your tenant, account, user name or client ID
  • Query text, filter values or parameters
  • Results, rows or any directory data
  • Columns refused for permission (they describe your account, not Graph)
  • Machine name, OS user, device or install ID
  • Usage, clicks, errors or crash reports

How it is kept small

  • Kustodian builds the event itself; no SDK, so nothing is collected on the side
  • A finding already known on your machine isn’t sent again
  • A send that fails is dropped, never retried or queued
  • Builds from source and forks send nothing: the destination is only built into official releases

Where it goes and how long it is kept

Events go to an Azure Application Insights resource in an EU region, owned by the Kustodian maintainer. Microsoft processes them as Azure’s data processor. Application Insights stores the client IP as 0.0.0.0, and Kustodian sends 0.0.0.0 as the location IP too, so no address or location is kept. Events are kept for 90 days, then deleted. They are used only to decide which tables get built-in query settings, and are not sold or shared with anyone.

Opting in and out

The first time you start a version of Kustodian that has this, it asks once. Nothing is shared before you answer, and closing the question without answering shares nothing (it asks again at the next start). To change your answer, open Settings → Graph compatibility findings and tick or untick Share Graph compatibility findings. It applies at once. The choice is stored as "telemetry" in settings.json in Kustodian’s data folder.

Check it yourself

Kustodian is open source. The code that builds and sends the event is AppInsightsTelemetry.cs, and what triggers it is SharedProbeCache.cs. Questions or concerns: open an issue.
