# Create Entra ID application: design

Date: 2026-10-22. Status: for the owner's review.

Mockups (in `kustodian/docs/design/mockups/`):

- `EntraApp.dc.html`: choose permissions. One permission is shown unticked so the "you lose" line appears.
- `EntraAppCreated.dc.html`: created, with the next steps.
- `EntraAppRefused.dc.html`: creation refused, and the partial case.

Marking used below: **Owner** means the owner decided it. **My call** means I chose it on the owner's behalf; it can be changed.
Anything unmarked follows from those two or from Microsoft's documentation, which is linked where it matters.

## 1. Why

Kustodian signs in with the Azure CLI's public client by default. That client carries whatever Microsoft pre-authorized for it.
Many Graph tables, advanced hunting (`ThreatHunting.Read.All`) and some Resource Graph uses are refused for missing permissions.
The answer today is "use your own app registration", which means leaving Kustodian for the Entra admin center, finding the right
permissions table by table, and typing a client ID back in.

This feature makes that one step inside Kustodian (**Owner**). A user signed in with the Azure CLI client:

1. clicks **Create Entra ID application**;
2. sees the least set of delegated permissions that gives full functionality, grouped by what they unlock;
3. unticks what they don't want and sees what they lose;
4. clicks **Create**, and Kustodian creates the app registration through Graph with the signed-in token.

## 2. Goals

- One click from "No permission" to an app registration that can read everything Kustodian can query.
- The permission list is derived from data (Microsoft's permissions file and the source definitions), never a hand-written list.
  It is the least set: one permission that covers many tables wins over many narrow ones (**Owner**).
- The user sees exactly what will be created before anything is (**Owner**).
- After creation, Kustodian offers admin consent for the whole tenant (**Owner**). Then it asks whether to switch to the new app
  and sign in with it, or just show the client ID (**Owner**).

## 3. Non-goals

- Editing or deleting an existing app registration. Kustodian creates one and stops there. Changes happen in the Entra admin
  center.
- Application permissions (app roles), client secrets and certificates. Kustodian is a delegated public client and nothing else.
- Granting consent through Graph (`oauth2PermissionGrants`). Section 7 explains why.
- Sovereign clouds. Kustodian supports only the public cloud today.

## 4. Anti-goals

- **Never offer a write permission** (**Owner**). Kustodian only reads. A permission is offered only when its name contains
  `.Read` and does not contain `Write`. `Directory.AccessAsUser.All` and `*.ReadWrite.*` never appear, even for the eight tables
  only they unlock. Those tables are listed as "not reachable with read permissions" (section 5.4).
- Nothing is created, granted or saved without a click on a button that says so. Opening the dialog makes read requests only.
- No token, authorization header or consent URL `state` value is ever logged or written to the run log. App and service
  principal IDs may be logged.

## 5. The permission list

### 5.1 Where the data comes from

| Source | Requirement | Where it is declared |
|---|---|---|
| Graph tables | Every delegated read permission that can `GET` the table's path | Microsoft's `permissions.json`, through the schema tool |
| Advanced hunting | Graph `ThreatHunting.Read.All` | Beside `HuntingClient` |
| Azure Resource Graph | Azure Service Management `user_impersonation` | Beside the ARG source |

Today `GraphTable.Permissions` keeps only the permissions Microsoft marks least-privileged for each path. That is not enough
for a covering set. `Directory.Read.All` is never least-privileged for `users`, but it covers `users`, `groups`, `applications`,
`devices` and 20 more tables. So the schema tool gains a second output.

`graph-permissions.json` is generated by `tools/schema` next to `graph-beta.json` and embedded in `Kustodian.Graph`. It is not
hand-edited. For each `DelegatedWork` permission that can `GET` at least one table path (any marker, not just `least=`), it
holds:

- `name`;
- `adminConsent`: the scheme's `requiresAdminConsent`;
- `description`: the scheme's `userDescription`;
- `tables`: the table paths it can read, matched exactly as `GraphPermissions.NormalizePath` matches them.

`GraphPermissions.ReadDelegated` and the table's own `Permissions` (least-privileged, used by Explain and the No permission
error) stay as they are.

Hunting and ARG declare their requirement in code as a `SourcePermission` record: resource app ID, scope name, admin-consent
flag, and the label of what it unlocks. `ThreatHunting.Read.All` requires admin consent (`permissions.json`, `DelegatedWork`).
`user_impersonation` on Azure Service Management (app ID `797f4846-ba00-4fd7-ba43-dac1f8f63013`) does not.

### 5.2 Choosing the least set

Kustodian computes the set when the dialog opens. It is pure and deterministic, and covered by unit tests over a fixture:

1. Take the read-only permissions (section 4) and the tables each one covers.
2. Run a greedy set cover over all tables that have permission data: repeatedly pick the permission that covers the most tables
   not yet covered. Break ties by not requiring admin consent first, then by name.
3. Add the source permissions (hunting, ARG) as they are.

On today's schema this gives **125 Graph permissions covering 469 of the 485 tables** that have permission data, plus
`ThreatHunting.Read.All` and `user_impersonation`. The other 270 tables have no delegated permission data at all. They are
outside the list and the dialog says so in one line.

Greedy cover is not always the true minimum. It is close, and its picks are easy to explain: "this one covers 127 tables".
**My call.**

### 5.3 Grouping and default ticks

The dialog groups permissions in three top-level groups, with subgroups where they help (**Owner**).

**Graph**

Subgroups are the Graph data areas from `graph-areas.json`, in `GraphAreas.Names` order, except Security, which moves to the
Security group. A permission sits under the area where most of its tables are, with ties going to the first area in that
order. Each row still lists its tables in every area it covers.

**Security**

- Advanced hunting: `ThreatHunting.Read.All`.
- Graph's Security area: alerts, incidents, threat intelligence, Global Secure Access and similar.

Risk and identity protection stays under Graph: it is Entra ID data. **My call.**

**Azure Resources**

- Resource Graph: `user_impersonation`.

**Default ticks (Owner)**

| Default | Areas |
|---|---|
| Ticked | Users, groups and directory; Apps and permissions; Sign-in and audit logs; Risk and identity protection; Access reviews and privileged roles; Policies and Conditional Access; Devices and Intune; Security (both subgroups); Azure Resources |
| Unticked | Mail, Teams and files; Reports and usage; Other (this is where printers, education, search and connectors land) |

A permission is ticked when its home area (the area it is grouped under) is ticked. That way a group shown unticked holds no
ticked rows. **My call.** A permission homed in an unticked area that also covers a table in a ticked area stays unticked. That
table shows "not covered" until the user ticks the permission. On today's schema the defaults are 44 Graph permissions plus
hunting and ARG: 46 permissions covering 252 tables. 44 of them need admin consent.

### 5.4 What the dialog shows per permission

- A checkbox and the permission name in mono.
- An **Admin** tag when it requires admin consent.
- What it unlocks, as "127 tables" plus up to three table names. A disclosure lists them all; for a source permission it names
  the source instead ("Advanced hunting").
- When the row is unticked, the tables it alone covers among the ticked set: "You lose 3 tables: riskyUsers, …". A table also
  covered by another ticked permission is not lost.
- A group header has a tri-state checkbox (all, none, mixed) and its own count, such as "Devices and Intune · 5 permissions ·
  222 tables".

The footer keeps a running total, such as "46 permissions · 252 of 303 tables · 44 need admin consent". A muted line says that
133 tables have no published delegated permission and 8 are reachable only with write permissions, which Kustodian doesn't ask
for.

## 6. The button and the dialog

### 6.1 When the button shows

The button shows on the sign-in screen, in the active account's "What this sign-in can read" card (mockup SignIn), as
**Create Entra ID application…**. It shows only when the active account's client ID is the Azure CLI client
(`ClientConfig.IsAzureCli`) and the account is not expired.

It is enabled when the account's last Graph `scp` (`AccountInfo.Scopes`, already stored) contains `Application.ReadWrite.All`
or `Directory.AccessAsUser.All`. `AppRegistration.Create` alone is not enough, for two reasons:

- It is least-privileged for `POST /applications`
  ([Create application](https://learn.microsoft.com/graph/api/application-post-applications)).
- `POST /servicePrincipals` needs `Application.ReadWrite.All`
  ([Create servicePrincipal](https://learn.microsoft.com/graph/api/serviceprincipal-post-serviceprincipals)).

So a token with only `AppRegistration.Create` would always stop halfway. **My call.** Kustodian doesn't assume what the Azure CLI
token carries; the check is at runtime. When neither scope is present, the button is disabled and a muted line says why: "This
sign-in can't create app registrations (it needs Application.ReadWrite.All)."

The same action is the palette command **Create Entra ID application** (group "Account"). It is enabled under the same
conditions and opens the sign-in screen with the dialog open. Every action is a command.

The hunting 403 message (`HuntingClient.NoPermission`) and the Graph No permission error currently say "use your own app
registration". The sources don't know the client ID. So when a run's outcome is `noPermission` and the active account is the
Azure CLI client, the run status shows a **Create Entra ID application…** button beside the message, running the same command.
**My call.**

### 6.2 The dialog (mockup EntraApp, board 1)

A modal over the sign-in screen. Esc and a click outside close it, except while it is creating; then neither does anything and
the Cancel button is disabled.

It has two columns.

**Left: the permission groups** (section 5.3), scrollable, with the footer totals.

**Right: what will be created.** The summary updates as ticks change.

- **Name:** a text field, by default `Kustodian (<username>)`, editable and required (1 to 120 characters, trimmed). **Owner**
  asked for the example; the length limit is **My call**.
- **App registration:**
  - single tenant (`AzureADMyOrg`) in `<tenant name>` (`<tenant ID>`);
  - public client with redirect URIs `http://localhost` and `https://login.microsoftonline.com/common/oauth2/nativeclient`;
  - "Allow public client flows" on, for device code.
- **Service principal:** the enterprise app in your tenant, so the app can be consented to and signed in to.
- **API permissions (delegated):** Microsoft Graph · N, Azure Service Management · 1 or 0. Nothing is granted by creating it.
- **Owner:** you (step 3 in section 6.3 makes sure of it).
- The buttons **Cancel** and **Create**. Create is disabled with no permission ticked or an empty name.

The dialog's opening request (`entraApp.plan`) reads only.

- **Tenant:** it makes one Graph call, `GET /organization?$select=id,displayName`. The app is created in the tenant the Graph token
  is for (its `tid`), which isn't always the account's home tenant: a guest, or a sign-in pinned to another tenant. Every place
  that names the tenant uses that ID and display name: the summary, the consent URL, "Open in Entra" and the saved
  `signIn.tenant`. **My call.**
- **Permission list:** the rest is the computed list. Permission IDs are looked up at Create (section 6.3).

### 6.3 Create

Create runs these steps. The dialog shows them as a checklist with the current one spinning.

1. **Look up permission IDs.** `requiredResourceAccess` needs each scope's GUID. Kustodian reads them from the tenant:
   - `GET /servicePrincipals(appId='00000003-0000-0000-c000-000000000000')?$select=id,oauth2PermissionScopes` for Microsoft
     Graph;
   - the same for Azure Service Management when `user_impersonation` is ticked.

   A ticked permission the tenant's Graph doesn't define is dropped and named in the result ("Not in your tenant: X"). Its
   `type` (`Admin` or `User`) from the tenant overrides the bundled admin flag for the consent step.
2. **Create the app.** `POST /v1.0/applications` with:
   - `displayName`;
   - `signInAudience: "AzureADMyOrg"`;
   - `isFallbackPublicClient: true`;
   - `publicClient.redirectUris`: the two above;
   - `requiredResourceAccess`: one entry per resource, each scope as `{id, type: "Scope"}`.

3. **Make the user an owner.** Microsoft adds a non-admin creator as owner, but not an admin (for example, a Cloud Application
   Administrator). Kustodian adds the owner itself:
   - read the user's object ID from `GET /me?$select=id`;
   - `POST /applications/{id}/owners/$ref` with `{"@odata.id": "https://graph.microsoft.com/v1.0/directoryObjects/{me}"}`.

   An "already exists" answer counts as success. Any other failure doesn't stop the create; the result says "You were not added
   as owner" with Graph's message. **My call.**
4. **Create the service principal.** `POST /v1.0/servicePrincipals {appId}`. A new app can take a moment to replicate. A 404 or
   400 naming the app is retried up to 5 times, with 1, 2, 4, 8 and 8 seconds between tries.

All calls go through the existing Graph HTTP client: its token handler, no redirects, and the run log without bodies or tokens.

### 6.4 Failures

| What happens | What the user sees |
|---|---|
| `403 Authorization_RequestDenied` on step 2 | "Your tenant doesn't let you register applications. An admin can turn on 'Users can register applications', give you the Application Developer role, or create the app for you." Nothing was created. |
| Step 1 refused (no read on service principals) | "Kustodian couldn't read Microsoft Graph's permission list in your tenant." With Graph's message. Nothing was created. |
| Step 4 fails after its retries, or answers 403 | The app exists without a service principal. The dialog says so with the client ID and offers **Try again**, which retries step 4 only, and **Open in Entra**. On a 403 it adds: "You can't create its enterprise application; an admin's consent (next step) creates it." The consent step still works then, because admin consent creates the service principal. Kustodian never deletes the app on its own (**My call**: deleting is a write the user didn't ask for). |
| Sign-in expired, or ARM consent needed | The existing `signInNeeded` and `consentNeeded` handling. |
| The user closes Kustodian mid-create | Whatever was created stays. A later Create makes a new app; nothing is remembered between runs. |

Each failure keeps the dialog open with the user's choices intact.

### 6.5 Created (mockup EntraApp, board 2)

The dialog's content switches to:

- **Created** with the app's name, client ID and tenant ID, each with a copy button. Also "Open in Entra admin center" (the app's
  Overview blade, by client ID).
- **1. Grant for the whole tenant** (section 7). This step is optional and shown first, because a non-admin's sign-in can't
  succeed before it when admin-consent permissions are ticked.
- **2. What now?** (**Owner**), two choices:
  - **Switch to this app and sign in** (primary): section 8.
  - **Just show me the client ID**: closes the dialog. Nothing is saved; the client ID stays in the account card's note until
    the screen is left.

## 7. Admin consent

Two options were weighed:

- **The admin consent URL in the system browser** (chosen):
  `https://login.microsoftonline.com/{tenantId}/v2.0/adminconsent?client_id={appId}&scope=https://graph.microsoft.com/.default&redirect_uri=https://login.microsoftonline.com/common/oauth2/nativeclient&state={random}`.
  - With `/.default` it asks for all the permissions the app registration lists, across resources, so Azure Service
    Management is included ([Admin consent on the Microsoft identity platform](https://learn.microsoft.com/entra/identity-platform/v2-admin-consent)).
  - Microsoft's own page shows the admin exactly what is granted, and only an admin who may grant can finish it.
  - It needs no extra scope on the Azure CLI token.
  - The same link can be sent to an admin by a user who isn't one.
- **`POST /oauth2PermissionGrants` with `consentType: AllPrincipals`.** It needs `DelegatedPermissionGrant.ReadWrite.All` on
  the token and a consenting role. It grants without a review screen, which Microsoft cautions against. It is also a write
  Kustodian would make on the tenant without Microsoft's confirmation. Rejected.

The step offers:

- **Open admin consent page**: Kustodian opens the URL in the system browser through a new bridge command,
  `entraApp.openConsent {appId}`. The command builds the URL itself from the app ID and the account's tenant and opens only
  that. It never takes a URL from the UI.
- **Copy link for an admin**: the same URL, without `state`, to the clipboard.
- **Check again**: finds the service principal by `appId` (`GET /servicePrincipals(appId='{appId}')?$select=id`), then reads
  `GET /oauth2PermissionGrants?$filter=clientId eq '{spId}' and consentType eq 'AllPrincipals'` and the scopes granted. It shows "Granted for the tenant: 44 of 44 admin permissions" or names what is missing. The browser page
  lands on a blank `nativeclient` page, so Kustodian can't learn the result by itself; Check again is how it finds out.

**Who can grant (hint only).** On entering this step Kustodian reads the user's active directory roles
(`GET /me/memberOf/microsoft.graph.directoryRole?$select=roleTemplateId`). Global Administrator, Privileged Role Administrator,
Cloud Application Administrator, Application Administrator and AI Administrator can grant tenant-wide consent for delegated
Graph permissions
([Grant tenant-wide admin consent](https://learn.microsoft.com/entra/identity/enterprise-apps/grant-admin-consent)).

- With one of these roles, **Open admin consent page** is the primary button.
- Without one, **Copy link for an admin** is primary and a line says: "You can't grant this yourself. Send the link to an
  admin, then click Check again."
- If the read fails, both buttons are equal and nothing is claimed.

A PIM-eligible but inactive role reads as no role, which is right: it can't grant until it is activated.

**Users who aren't admins** consent for themselves at first sign-in (**Owner**). That works only for permissions that don't
need admin consent. With the default ticks, 44 of 46 need it, so the dialog says plainly: "Until an admin grants these, signing
in with this app will ask for admin approval." If the tenant has the admin consent workflow on, Microsoft's sign-in page offers
"Request approval" by itself.

## 8. Switching to the new app

Kustodian already supports "My own app registration": `SignInDefaults(ClientId, Tenant)` in `settings.json`, and
`account.signIn {clientId, tenant}`. **Switch to this app and sign in**:

1. writes `signIn.clientId = <appId>` and `signIn.tenant = <tenantId>` through `settings.set`, so the sign-in screen starts with
   "My own app registration" filled in from then on;
2. calls `account.signIn {clientId, tenant, deviceCode: false}`, the same interactive sign-in as the screen's own button, with
   the device-code fallback the screen already has;
3. on success, the new account becomes active. The Azure CLI account stays in "Accounts on this computer" and can be used or
   signed out as before.

If sign-in fails because consent is missing (`AADSTS65001` or `AADSTS90094`), the error says "This app still needs an admin
to grant its permissions", and the consent step is shown again. The settings stay written, since the app is the user's choice
now.

## 9. Bridge and code layout

New handler `EntraAppHandler` (`kustodian/src/Kustodian/Bridge/Handlers/`):

| Command | Answer |
|---|---|
| `entraApp.plan` | `{canCreate, reason?, defaultName, tenantId, tenantName (from `/organization`), groups[], unreachable: {noData, writeOnly}}`. Each group is `{id, title, subgroups[]}`. Each permission is `{resource, name, adminConsent, tables[], area, ticked}`. |
| `entraApp.create {name, permissions[]}` | `{appId, objectId, servicePrincipalId?, tenantId, ownerAdded, dropped[]}`. Progress goes out as `entraApp.step` events. |
| `entraApp.retryServicePrincipal {appId}` | As `create`, step 4 only. |
| `entraApp.consentStatus {appId}` | `{granted[], missing[]}`. It finds the service principal by `appId`, because admin consent may have created it. |
| `entraApp.canGrant` | `{canGrant: true \| false \| null}` |
| `entraApp.openConsent {appId}` | `{}` |
| `entraApp.consentLink {appId}` | `{url}` |

Logic lives in `kustodian/src/Kustodian/Auth/EntraApp/`:

- `PermissionPlanner`: pure cover and grouping, unit-tested;
- `EntraAppClient`: Graph calls, tested with a fake HTTP handler.

The schema tool change and `graph-permissions.json` go in `Kustodian.Graph/Schema` and `tools/schema`.

The UI is `web/src/signin/create-app-dialog.tsx`, with tests beside it. The palette command goes in the existing command
registry.

No browser storage: ticks and name live in component state. The rule "menus close on click-outside or Esc" covers the
dialog's table-list disclosures too.

## 10. Testing and verification

- **Unit:**
  - the planner on a fixture: cover, tie-breaks, read-only filter, grouping, home-area default ticks, and "you lose" lists;
  - the schema tool's new output on `permissions-excerpt.json`;
  - `EntraAppClient` request bodies, adding the owner, the replication retry, 403 mapping on create and on the service principal, and the tenant from `tid`;
  - the consent URL builder;
  - the dialog's states with the bridge mock.
- **Manual (the owner, on a test tenant):** the owner does these, never the builder (section 12):
  1. create as a non-admin, then as an admin;
  2. the tenant with "Users can register applications" off;
  3. admin consent from the system browser, then Check again;
  4. switch and sign in;
  5. a hunting query and an ARG query with the new app.

  Add these to `kustodian/docs/manual-checks.md`.

## 11. What is left to the builder

- Copy beyond what is quoted here, the exact layout within the mockup, and icons.
- How `entraApp.step` events are shaped.
- Whether the planner runs once per app start or per dialog open. It is fast either way.

## 12. Safety rules for building it

The builder never creates an app registration, grants consent, or calls Graph with the owner's account. Tests use fakes; manual
checks are the owner's.
